## Glossary

- **User:** person registered in the system.
- **Visitor:** person who has not registered yet.
- **Account:** a user's account in a currency (ARS or USD), with balance, alias, and external account number.
- **External account number:** 22-digit numeric identifier (equivalent to a CBU/CVU) for receiving money from outside.
- **Alias:** human-readable account identifier, made up of 3 words separated by a period.
- **External provider:** third-party system (bank, wallet, or collection network) that sends deposits to accounts. It authenticates with an API key and signature.
- **Settlement account:** system account, one per provider, from which external deposits are debited.
- **External deposit:** money that arrives in an account from an external provider.
- **Ledger entry:** immutable accounting record of a debit or credit on an account.
- **Operation ID:** unique identifier sent by the provider and used as the idempotency key.

## CU-01: Register user

- **Primary actor:** unregistered visitor.
- **Goal:** to have a registered user.
- **Trigger:** `POST /users` with first name, last name, email, date of birth, password, and accepted terms.

**Preconditions**

- The visitor is not registered.

**Main flow**

1. The system validates that the entered data is correct (required fields, first and last names without numbers or special characters (except accents, spaces, apostrophes, hyphens, and ñ), email format, age greater than or equal to 18, secure password, accepted terms).
2. The system verifies that the email is not already registered.
3. The system saves the user with the hashed password.
4. The system returns status code 201.

**Alternative flows**

- **A1. Invalid data (step 1):** required fields are not correct. Empty fields, first and last names with numbers/special characters (except accents, spaces, apostrophes, hyphens, and ñ), incorrect email format, underage, insecure password, terms not accepted. Returns status code 400.
- **A2. Duplicate email (step 2):** the email already exists in the system. Returns status code 409.
- **A3. Technical failure midway through the process:** no data is saved in the system. Everything is rolled back and it returns status code 500.

**Postconditions**

- **Success:** the user exists, without an account.
- **Failure:** the user does not exist.

**Business rules involved**

- The password must have a minimum length of 10 characters, a maximum of 72 bytes, and include at least one uppercase letter and one special character.
- Password stored with a hash using BCrypt; it is not shown in responses or logs.
- The email is normalized (without spaces and in lowercase) before comparing it.
- If two simultaneous registrations arrive with the same email, only one is created (the first to arrive). This is guaranteed by a UNIQUE constraint in the database, and the other receives status code 409.
- Status code 201 returns id, first name, and email.

## CU-02: Open account

- **Primary actor:** existing user.
- **Goal:** to have an account in a currency.
- **Trigger:** `POST /accounts` with the currency.

**Preconditions**

- The user is registered and authenticated.

**Main flow**

1. The system validates that the user is authenticated.
2. The system validates that the currency is correct.
3. The system validates that the user does not already have an account in that currency.
4. The system creates the account with balance at 0, an autogenerated alias, external account number (CBU/CVU), and active status.
5. The system returns status code 201, with id, currency, balance, alias, external account number, and status.

**Alternative flows**

- **A1. Unauthenticated user (step 1):** the user is not authenticated. Returns status code 401.
- **A2. Invalid currency (step 2):** the currency is not valid. Returns status code 400.
- **A3. Duplicate account (step 3):** an account already exists in that currency. Returns status code 409.
- **A4. Technical failure midway through the process:** everything is rolled back, the account is not created, and it returns status code 500.

**Postconditions**

- **Success:** a new account exists associated with the user, with balance 0, defined currency, generated alias and account number, and active status.
- **Failure:** the account is not created.

**Business rules involved**

- Allowed currencies: ARS, USD.
- One account per currency per user, guaranteed with `UNIQUE (user, currency)`. If two simultaneous requests arrive, the last one to arrive receives status code 409.
- The owner comes from the token, not from the request body. The client does not send the user ID; the server takes it from the JWT.
- If the token is expired or invalid, it returns status code 401.
- The external account number is made up of exactly 22 numeric digits. The system generates the number and verifies that it does not already exist in the system. Uniqueness is guaranteed with a UNIQUE constraint in the database; if it fails, another value is attempted.
- The alias is autogenerated with a maximum of 20 characters and a minimum of 6. It must contain random words from a dictionary, 3 words separated by a period, e.g. `saco.molinete.acecho`. It is validated that it does not already exist in the system. Uniqueness is guaranteed with a UNIQUE constraint in the database; if it fails, another value is attempted.
- The alias keeps the lowercase format by default. Numbers are allowed, but no special characters except `.`.

## CU-03: Log in

- **Primary actor:** unauthenticated user.
- **Goal:** to authenticate the user so they can access their account.
- **Trigger:** the user sends `POST /auth/login` with their login data (email, password).

**Main flow**

1. The system validates the request format (required fields, email format).
2. The system validates that access is not blocked due to attempts.
3. The system looks up the user by normalized email (without spaces and in lowercase).
4. The system compares the password with the hash or performs a fake comparison if the user does not exist.
5. The system generates an access token.
6. The system returns status code 200, Bearer-type access token, and expiration time.

**Alternative flows**

- **A1. Malformed request (step 1):** required fields are malformed. Returns status code 400.
- **A2. Maximum retries (step 2):** the email or IP exceeded the failed-attempt limit within the window. Returns status code 429 with the message "The maximum number of login attempts has been exceeded. Please try again later" and the `Retry-After` header.
- **A3. Invalid credentials (step 4):** the email does not exist or the entered password is not correct for the presented email. Returns status code 401 and the message "The email or password are not correct", and the attempt is recorded as failed, adding 1 to the IP and email counters.
- **A4. Technical failure in the process:** the access token cannot be generated or something in the process fails. The user is not logged in and it returns status code 500.

**Postconditions**

- **Success:** a valid access token was issued for the user, and the email attempt counter is reset.
- **Failure:** no token was issued.

**Business rules involved**

- If there was a non-expired token, a new one is created and the previous one remains until it expires.
- Whether the email does not exist or the password is incorrect, it returns the same status code (401), the same message, and a comparable response time, to avoid revealing information about the database.
- Each failed attempt adds to the email and IP counters, even if the email does not exist. Upon reaching 6 failures per email or 20 per IP within 15 minutes, new attempts are blocked for 15 minutes and it returns 429. It returns 429 during the block even if the data is correct.
- Malformed requests (400), technical failures (500), and blocked attempts are not added to the counter or do not extend the block time (if any).
- The system performs a fake BCrypt comparison when the user does not exist, in order to prevent malicious agents from comparing times between the existing-email and non-existing-email cases.
- Passwords and tokens are not recorded.
- Failed attempts are recorded with a tracking ID.
- A successful login resets the email counter.
- The token expires after 15 minutes.

## CU-04: Receive external deposit

- **Primary actor:** external provider.
- **Goal:** for the provider to deposit an amount into an existing account.
- **Trigger:** the provider sends `POST /external-deposits`, authenticated with an API key and signature, with a unique operation ID, amount to send, currency, and external account number.

**Preconditions**

- The provider is registered and has a valid API key and signing secret.

**Main flow**

1. The system validates that the API key and signature are valid.
2. The system validates that the amount is greater than 0 and that the currency is supported.
3. The system verifies that the provider has not exceeded the request limit per minute (maximum 10 per minute per provider).
4. The system verifies whether the operation ID has already been processed.
5. The system looks up the destination account by its external account number.
6. The system validates that the account is active and that the currency matches.
7. The system verifies that the settlement account balance covers the amount.
8. The system records a debit in the provider's settlement account and a credit in the destination account (two ledger entries that sum to zero) and updates both balances.
9. The system saves the external deposit as COMPLETED.
10. The system returns status code 201 along with the operation ID given by the provider (used as the idempotency key), the deposit ID generated by the system, amount, currency, date, destination account, and status.

**Alternative flows**

- **A1. Invalid API key or signature (step 1):** returns status code 401.
- **A2. Amount less than or equal to 0 or unsupported currency (step 2):** amount less than or equal to 0, unsupported currency, or missing fields. Returns status code 400.
- **A3. Request limit reached (step 3):** returns status code 429 and the `Retry-After` header.
- **A4. Same ID with the same content (step 4):** returns status code 200 and returns the original result.
- **A5. Same ID with different content (step 4):** returns status code 409.
- **A6. Non-existent account (step 5):** returns status code 404.
- **A7. Inactive account or currency mismatch (step 6):** returns status code 422.
- **A8. Insufficient settlement account balance (step 7):** returns status code 422.
- **A9. Technical failure midway through the process:** everything is rolled back and it returns status code 500 with a tracking ID.

**Postconditions**

- **Success:** balances changed by the exact amount, two new ledger entries exist, the external deposit is saved as COMPLETED, and the idempotency key is associated with its result.
- **Failure:** nothing changes in balances, ledger entries, or deposits.

**Business rules involved**

- The API key is unique and has an expiration time of 30 days.
- Each request carries a timestamp and a signature calculated over method, path, timestamp, and body; it is rejected if the timestamp deviates by more than about 5 minutes.
- If the key or signature fails, it returns status code 401 with the same message, without clarifying which one failed.
- If the operation ID is the same with different content, it returns status code 409.
- The API key is stored hashed and is shown only once when it is created.
- The settlement account and the destination account are always locked in the same order (by ID) to avoid deadlocks.
- Uniqueness per operation ID is guaranteed with a `UNIQUE (provider, operation ID)` constraint in the database. If two identical requests arrive at the same time, only one is processed.
- The signing secret is stored encrypted and is not recorded in logs.

## CU-05: Check balance

- **Primary actor:** authenticated user.
- **Objective:** allow the user to check the balance of their account.
- **Trigger:** the user sends `GET /balance` with the authentication token and, optionally, the currency as a parameter `(?currency=ARS)`.

**Preconditions**

- The user is authenticated.

**Main flow**

1. The system validates that the token is valid.
2. If a currency was selected, the system validates that it is correct.
3. The system validates that the user has an account in that currency.
4. The system returns code 200 with the account balance, the currency, the query date and time (UTC), and the account status.

**Alternative flows**

- **A1. Expired or invalid token (step 1):** returns code 401.
- **A2. Invalid currency (step 2, only if a currency was selected):** returns code 400.
- **A3. Non-existent account for that currency (step 3, only if a currency was selected):** returns code 404.
- **A4. No currency and no accounts (step 3):** returns code 200 with an empty list.
- **A5. Technical failure mid-process:** the balance is not shown and it returns code 500 with a tracking id.

**Postconditions**

- **Success:** the balance was returned; no data was modified.
- **Failure:** the balance was not returned; no data was modified.

**Business rules involved**

- The balance reflects only confirmed operations up to the time of the query, excluding those in progress, and it is not served from a stale cache.
- The owner comes from the token, not from the request. A user can only see their own accounts.
- The amount is returned with 2 decimals, and balances are not written to the logs.
- The GET response is always a list of balances, even if it has only one element.

## CU-06: Look up recipient

- **Primary actor:** authenticated user.
- **Objective:** look up basic data of an account holder by alias or account number, to confirm who the money will be sent to.
- **Trigger:** the user sends `GET /accounts/lookup?identifier={alias_or_accountNumber}`, with their authentication token.

**Preconditions**

- The user is authenticated.

**Main flow**

1. The system validates that the token is valid.
2. The system validates that the query limit has not been exceeded.
3. The system validates that the format is valid (account number and alias).
4. The system validates that the account exists and is not inactive.
5. The system returns code 200 with first name, last-name initial, alias, and currency.

**Alternative flows**

- **A1. Expired or invalid token (step 1):** returns code 401.
- **A2. Query limit exceeded (step 2):** returns code 429 and the `Retry-After` header.
- **A3. Invalid query format (step 3):** returns code 400.
- **A4. Inactive or nonexistent account (step 4):** returns code 404 with the message `The entered account does not exist`.
- **A5. Technical failure mid-process:** no data is shown and it returns code 500 with a tracking id.

**Postconditions**

- **Success:** the account holder's data was successfully returned: first name, last name, alias, and currency.
- **Failure:** no data was returned. No data was modified.

**Business rules involved**

- The account holder's last name is returned abbreviated. Only the initial is shown, e.g., `Salvattore -> S.`. If the last name is compound, only the first initial is shown, e.g., `Di Tella -> D.`
- The query limit is 10 every 30 minutes per user (with the id from the token) and 20 every 30 minutes per IP. Every query that reaches the lookup counts, whether or not the account exists. It is defined per user. Malformed requests (400) do not add to the counter; blocked requests do not extend the block.
- If the account holder has multiple first names, only the first one is shown.
- The account number must have 22 numeric digits; the alias must be 3 words of 6 to 20 characters.
- The alias is normalized before performing the lookup (without spaces and in lowercase).
- Internal id, email, or personal data are never returned.
- Looking up by account number also returns the alias, and vice versa.
- Lookups are logged with a tracking id, without storing personal data, to detect abuse patterns.
- If the identifier belongs to the user's own account, it is returned the same way.

## CU-07: Transfer

- **Primary actor:** authenticated user.
- **Objective:** move money from their account to another user's account.
- **Trigger:** the user sends `POST /transfers` with their authentication token, the alias or account number of the destination account holder, Operation ID (used as the idempotency key), currency, amount, and description.

**Preconditions**

- The user is authenticated.

**Main flow**

1. The system validates that the token is valid.
2. The system validates the request format (required fields, amount greater than 0 with at most 2 decimals).
3. The system validates that the idempotency key has not been used before.
4. The system validates the existence and status of the origin and destination accounts.
5. The system validates that the origin account is different from the destination account.
6. The system validates that the origin and destination accounts match in currency.
7. The system starts the transaction and locks both accounts, always in the same order (by id) to avoid cross locks.
8. The system evaluates the operation with the control policies (see CU-10) and obtains the decision: approved or under review.
9. The system verifies that the origin account balance covers the amount.
10. The system records a debit in the origin account and a credit in the destination account (two ledger entries that sum to zero).
11. The system updates both balances.
12. The system saves the transfer with COMPLETED status, together with the idempotency key and the result.
13. The system commits the transaction.
14. The system returns code 201 with the receipt, id, amount, currency, status, origin (first name and last name), destination (first name and last-name initial), date, and description.

**Alternative flows**

- **A1. Invalid or expired token (step 1):** returns code 401.
- **A2. Invalid request format (step 2):** returns code 400 with the field detail.
- **A3. Key already used, same content (step 3):** the transfer is not performed again; returns code 200 with the original receipt or 202 with `UNDER REVIEW` status if applicable.
- **A4. Key already used, different content (step 3):** responds 409 due to idempotency conflict.
- **A5. Nonexistent or inactive account (step 4):** returns code 422.
- **A6. Origin account equal to destination account (step 5):** returns code 400.
- **A7. Invalid currency (step 6):** the system does not perform the transaction and returns code 422.
- **A8. Operation under review (step 8):** the control policy leaves the operation in `UNDER REVIEW` status (see CU-10). The system saves the transfer as `UNDER REVIEW`, without debit or credit and associated with the idempotency key, commits that transaction, and returns the code defined by CU-10 for the review reason.
- **A9. Insufficient balance (step 9):** the transaction is rolled back and it returns code 422. No ledger entries are written.
- **A10. Simultaneous request with the same key:** only one is processed; the other receives the result of the first.
- **A11. Technical failure mid-process:** everything is rolled back, nothing remains half-done, and it responds 500 with a tracking id, without exposing internal details.

**Postconditions**

- **Success:** balances changed by the exact amount, two new ledger entries exist, the transfer is saved as COMPLETED, and the idempotency key is associated with its result. The event is recorded to publish to Kafka.
- **Pending review:** the transfer is saved as `UNDER REVIEW`, without debit/credit, and associated with the idempotency key. See CU-10 and CU-11.
- **Failure:** nothing changed in balances, ledger entries, or transfers.

**Business rules involved:**

- The amount must be in `BigDecimal`, greater than 0, with at most 2 decimals; if there are more than 2 decimals, it is rejected.
- The description is an optional field and can have a maximum of 200 characters.
- Ledger entries are immutable.
- Operations where the destination is the same as the origin account are not allowed.
- When simultaneous requests exist, only the first to arrive is processed; the rest receive the result of the first. This is guaranteed by a `UNIQUE` constraint in the database.
- The origin account cannot transfer an amount greater than the available balance it has.
- Transfers between accounts with different currencies are not allowed.
- Limit, anti-fraud, and review rules are not defined here: they are in CU-10. This use case only executes the evaluation and acts according to its decision.

## CU-10: Evaluate control policies (limits and anti-fraud)

- **Primary actor:** system (runs inside CU-07).
- **Objective:** decide whether an operation is approved or remains under review, according to limits and anti-fraud.
- **Trigger:** CU-07 invokes the evaluation with the origin account, destination account, amount, and currency of the operation.

**Preconditions**

- The origin account is locked within an ongoing transaction (so that totals are consistent).

**Main flow**

1. The system validates that the user's operations are not suspicious (anti-fraud).
2. The system validates that total daily operations do not exceed the $50,000,000 ARS daily restriction.
3. The system validates that the individual operation does not exceed the allowed $2,500,000 ARS.
4. The system returns the decision to CU-07: approved.

**Alternative flows**

- **A1. Block due to suspicious operations (step 1):** if the system detects a possible fraud attempt, CU-07 returns code 400 and the account and transfer status is set to `UNDER REVIEW`.
- **A2. Operations exceed the allowed total daily maximum amount (step 2):** the system leaves the transaction in `UNDER REVIEW` status and CU-07 returns code 202.
- **A3. Individual operation exceeds the allowed individual maximum amount (step 3):** the system leaves the transaction in `UNDER REVIEW` status and CU-07 returns code 202.

**Postconditions**

- **Approved:** no data is modified; CU-07 continues with the balance verification.
- **Under review:** the operation and/or account enter `UNDER REVIEW` status, without debit/credit. All future debit/credit actions enter `UNDER REVIEW` status. An auditor later decides on the account and pending operations awaiting approval (see CU-11).

**Business rules involved:**

- If a transaction remains in `UNDER REVIEW` status and the account is not in `UNDER REVIEW` status, the user can continue operating, but that transaction counts toward the daily total. It is approved if the total excluding that transaction does not exceed the limit, or the auditor can authorize the excess.
- If a transfer is in `UNDER REVIEW` status, the total amount of that transfer, whether debit or credit, is held and will not be reflected in the origin account or the destination account.
- There is an anti-fraud system that detects suspicious operation patterns and blocks transactions indefinitely. Suspicion may arise from, e.g., several transfers to the same destination account in a short time; an unusual amount for the user's account; etc. The account enters `UNDER REVIEW` status, suspicious and future operations are recorded and left in `UNDER REVIEW` status, and an auditor must review the account and may decide whether it is suspended, escalated to financial authorities, or becomes `ACTIVE`.
- If the anti-fraud system pauses an account, until the account becomes `ACTIVE`, no operation can change status.
- If an individual operation exceeds $2,500,000 ARS, it enters `UNDER REVIEW` status for an auditor to review.
- If the total amount of daily operations from the origin account exceeds the allowed maximum ($50,000,000 ARS), this transaction enters `UNDER REVIEW` status, where an auditor must decide whether to approve this transfer or report it to the financial authorities to obtain a response before proceeding with it. "Daily" is taken as the last 24 hours.
- If the operation exceeds the individual operation amount of $2,500,000 and the total daily amount of $50,000,000, only the total daily amount flow is followed.
